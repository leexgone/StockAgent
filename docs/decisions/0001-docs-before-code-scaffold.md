# 0001 · 先固化文档与口径，不建代码骨架

- **状态**：接受
- **日期**：2026-10-24
- **决策者**：Steven Lee（产品方向）+ Claude（文档整理）

## 背景

原型已经有 7 个界面、约 3600 行，并且内建了不少真实业务规则（整手、费用、摊薄成本、涨跌停校验、仓位纪律、波动合成）。但规则散落在各页面的内联脚本里，同一个概念在不同页面用不同分母、不同小数位。此时如果直接开始写后端，会把「谁都能各写一套算法」的问题固化进服务端。

同时项目还没有服务端、没有存储、没有数据源。此时最容易犯的错是先搭一个看起来很专业的目录结构，再往里塞没定稿的逻辑。

## 决定

本轮工程初始化只做三类事：仓库卫生（`.gitignore` / `.gitattributes` / `.editorconfig`）、根 README 与 CLAUDE.md、`docs/` 规格与口径手册 + ADR。**不创建任何代码骨架目录**（`backend/`、`src/`、`package.json`、`pyproject.toml` 等）。

## 选项与取舍

- **A：文档先行（选）**。成本是这一轮看不到「能跑的后端」；收益是 P2 阶段可以把口径直接翻译成纯函数与验收用例，后端实现有唯一答案。
- **B：同时搭骨架（不选）**。目录会先于决策成型，之后每次改主意都要搬家；而且技术栈还没定（见 0003），搭了大概率要拆。
- **C：直接开始补功能（不选）**。原型已知有阻断缺陷（`07-backlog.md` A1），带着报错做新功能等于给坏地基加层。

## 后果

- 正面：`03-domain-rules.md` 成为数字的唯一来源；后续所有实现（含推送文案）必须引用它。
- 负面：仓库在一段时间内仍然「只有原型」，对外看不出进展；需要靠 ADR 和路线图保持方向感。
- 改回来的成本：低。真要建骨架时，新增的都是新目录，删除文档不影响运行。

关联：`0002`、`0003`、`06-roadmap.md` P0–P2。
