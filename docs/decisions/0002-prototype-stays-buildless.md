# 0002 · 原型保持零构建纯 HTML 形态

- **状态**：接受
- **日期**：2026-10-24
- **决策者**：Steven Lee

## 背景

`design/` 是无构建、无外部依赖、断网可跑的多页 HTML：双击即开，改一行刷新就看到。评审者（只有产品作者一人 + Claude）关心的是信息架构、交互闭环与数字口径，不是组件复用率。

同时 A 股业务的展示细节很杂：涨跌配色反惯例、小数位按品种不同、金额有「万」单位、净值要归一化到同一起点。这类东西用真实 DOM 直接写最快，套一层框架的抽象反而要先解决「样式令牌怎么进 JS」的问题（现有图表层已经是直接读 CSS 变量的）。

## 决定

继续保留零构建形态：每屏一个 HTML + 内联 `<script>`，共享 `assets/ui.css`（样式）、`assets/data.js`（数据与派生）、`assets/charts.js`（SVG 图表原语）。不引入打包器、框架、npm 依赖与 CDN 脚本。

## 选项与取舍

- **A：零构建多页（选）**。优点：改一处看一处、无环境依赖、原型即交付物；缺点：跨页状态只能靠 `localStorage` 与全局对象，重复逻辑容易散（已经出了 A1 事故）。
- **B：现在迁到 Vue/React + Vite（不选）**。组件化与状态管理更规整，但要先做一次全量重写，把已经验证过的交互重新验证一遍；构建链还会把「双击就能给别人看」这个便利换掉。
- **C：单页应用化（不选）**。7 个界面对应 7 个独立 URL 更利于逐屏评审与截图。

## 后果

- 正面：验证成本低，任何时候都能拿给人看；将来若迁移，`QW` 契约（见 `04`）就是天然的组件 props 边界。
- 负面：**跨页一致性没有编译期保障**，靠约定与人工检查。对策是把共享派生一律收进 `data.js`（CLAUDE.md 硬约定 2），并在 `06` P2 抽出纯函数配用例。
- 改回来的成本：中等。HTML/CSS 可复用，`<script>` 内联逻辑需要拆成模块；数据契约不变。
- 什么时候重新评估：出现「同一块 UI 在第 3 个页面重写」或「跨页状态需要实时同步」时。
