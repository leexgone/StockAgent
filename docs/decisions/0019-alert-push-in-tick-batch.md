# 0019 · 预警推送轮内合并（AlertPusher 边界批化）

- **状态**：接受
- **日期**：2026-11-20
- **决策者**：主人拍板（合并策略 = 仅轮内合并；单条形态 = 1 条保持原样、≥2 条才合并），Claude 协作探查与实施

## 背景

预警推送现为**逐条**：调度器每 60s 一轮 tick，`poll_once` 落库 + 同日 `(code,type)` 去重后，`rep.new_alerts` 逐条循环调 `AlertPusher`（scheduler.rs）。同日去重已保证每条预警每日至多推一次，但**集中爆发场景**（开盘/急跌轮，多只持仓同时跌破成本/止损）一轮可产十余条 → IM 刷屏。全链路此前零频控/合并机制。

探查核实：`AlertPusher` 全仓库仅 3 处消费（zimu-agent scheduler 与测试、zimu-server channel_push），原地改签名无外部破坏面；`push_log` 的 kind/detail 均自由字符串，subject 只出现在 detail 文本内 → 契约面零影响；15:05 盘后摘要（`summary_message` + `clip_by_lines`）已是「单条多行合并消息」先例。

## 决定

1. **D1 · 边界批化**：`AlertPusher` 签名原地由「一条 `NewAlertInfo` → bool」改为「一批 `Vec<NewAlertInfo>` → bool」（bool = 整批是否送达至少一个目标）。tick 推送点改**单次批调用 + 空批守卫**（无新预警不调用，避免「本轮 0 条」废消息）；批成功 `TickReport.alerts_pushed` = 全批条数、批失败 = 0。不返回 usize 成功条数——合并后送达粒度是**消息级**，条级计数是伪造不存在的粒度。
2. **D2 · 消息格式**（宿主 channel_push.rs 组装，恰一次）：
   - N=1：逐位复用现有 `alert_message`（`子木预警 · {name} {text}` / 主题 `预警 {code} {type}`），fixture 与契约样例兼容。
   - N≥2：正文 `子木预警 · 本轮 {n} 条` 标题行 + 逐行 `{序}. {name}（{code}）{text}`（含 code 便于回查 alerts 表）；主题 `预警批次 {n} 条`（不带 code 列表——subject 复制进每个 target 的 push_log detail 行，N 大时膨胀日志）。
   - **行序 = 判定产出序，不按 level 重排**：`level` 是方向/动作词汇非严重度轴（03 §11/§12 词汇纪律），判定序本身是 §12 定稿口径，确定性利于测试钉与回查。
   - 超长走既有 `clip_by_lines` 按行截断（与盘后摘要同语义）；被截掉的预警仍在 alerts 表与 Web 可查。（**长度条款 2026-11-23 被 ADR-0020 取代**：改全文透传归 robit 守卫，微信 ≤3 段分段、QQ 单条截断+省略号。）
   - push kind 恒 `alert_push`（前端 pushKind 词汇零改动）。
3. **D3 · 时机**：tick 内检测完立即发出，**零延迟**；不做跨 tick 时间窗聚合、不做紧急分级。
4. **D4 · 留痕**：一条合并消息 → 每通道每绑定会话一行 push_log（`push_to_bound` 完全不动，caps 参数化裸推语义保持）。
5. **D5 · 失败语义**：批失败（无通道送达）不重试、`alerts_pushed=0` 如实——同日去重已定格，与既有纪律同款；且与现状（逐条推送时通道不在线同样全灭）无恶化。

**「SchedulerCore 不动」纪律的适用范围澄清**：ADR-0017 与 scheduler.rs 头部纪律的该表述针对 inject_message / caps 场景——「宿主不反向侵入调度器、调度器不认通道」。本次是调度器自身**输出边界的批化**：何时推 / 推什么（轮内合并的编排决策）仍归调度器，文案 / 通道 / 留痕仍归宿主，纪律本身不变。

## 选项与取舍

- **合并策略**：仅轮内合并（**选**——检测完立即发零延迟；同日去重已保证零星场景每条每日至多一次、本身不刷屏，需压缩的恰是同轮爆发；实现无定时器无状态）；跨 tick 时间窗聚合（否——非零延迟 + 窗口缓冲状态机 + 定时冲刷逻辑，收益不成比例）；紧急分级（否——`level` 非严重度轴，按它分级 = 发明新语义，且订阅过滤归 C15 另案）。
- **边界形态**：原地改 `AlertPusher` 签名（**选**——消费仅 3 处全在仓库内，同批提交收口；单一语义）；新增并行批字段保留旧单条面（否——旧路径成死代码、双测试面、两套边界语义并存）。
- **返回值**：bool 整批（**选**——送达粒度即消息级）；usize 成功条数（否——伪造粒度，合并消息无法拆条计数）。
- **单条形态**：N=1 保持原样、N≥2 才合并（**选**——单条直达不稀释紧迫感、fixture 兼容）；统一合并格式（否——单条也套列表壳啰嗦、多一种消息样式）。
- **行序**：判定产出序（**选**——§12 定稿口径、确定性好测）；按 level 紧迫度重排（否——§11 词汇纪律，level 不是严重度轴）。

## 后果

**正面**：爆发轮 IM 消息每通道 1 条封顶（10 条预警 = 1 条消息）；N=1 行为逐位不变；契约 / fixture / 前端 kind 词汇零改动；零新增状态机。

**负面 / 接受的成本**：
- `TickReport.alerts_pushed` 粒度变粗（批级 all-or-nothing）——不落库、无下游消费者，仅测试断言面与日志素材。
- 极端爆发轮尾部截断（2000 字上限 ≈ 40–60 行）：IM 端丢尾部但 alerts 表与 Web 可查；C15 订阅体系落地时可再议（分级 / 摘要化）。（ADR-0020 起阈值放宽至微信 ~6000 字 / 3 段，QQ 仍 2000 字平台边界。）
- 批失败全损不重试：与现状通道不在线时等价，无恶化。

**以后要改回来得动哪里**：恢复逐条 → scheduler.rs 批调用点 + channel_push.rs `combine_alert_pushers`/`alert_batch_message` + 03 §12 推送打包小节，并置本 ADR 已取代；升级为时间窗聚合 → 新 ADR + 调度器内缓冲状态 + 03 §12 改写。
