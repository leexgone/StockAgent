# 0003 · 暂缓后端与前端框架选型

- **状态**：已取代（by 0005）——技术路线已定：Rust + robit 基建 / React 前端 / Python 行情 sidecar
- **日期**：2026-10-24
- **决策者**：Steven Lee

## 背景

工程初始化时通常需要一个技术栈。但当前阶段真正没定的是产品本身：微信接入方式（服务号需认证主体，个人不一定能申请）、持仓录入方式（手工 / 对账单 / 截图）、以及真实行情源选哪个——这三件事的结论会反过来决定服务端要长什么样。现在选定框架，大概率是为一个还不存在的需求选。

## 决定

不选，并显式禁止提前落地：不建 `backend/`、`src/`、`app/`，不加 `package.json` / `pyproject.toml` / `requirements.txt`，不写服务端代码。选型讨论留在 `07-backlog.md` C1–C3，等 `06-roadmap.md` P4 触发。

## 选项与取舍（记录候选，不作结论）

| 方向 | 候选 | 现在的倾向与理由 |
|---|---|---|
| 后端语言 | Python 3.13 + FastAPI + uv | 本机已装 Python 3.13 与 uv；A 股行情库（akshare/baostock/Tushare）生态几乎都在 Python；Anthropic SDK 的 Python 版最成熟。**最可能的答案，但没定** |
| | Node/TS + Fastify | 与前端同语言、类型定义可贯穿数据契约，但行情源要自己封 HTTP |
| 前端 | 保留零构建（见 0002） | 定稿后再评估是否组件化 |
| 存储 | 本地 SQLite / JSON 文件 | 单用户本地工具，未定 |

## 后果

- 正面：不被早期选择绑架；文档阶段能确定的是**契约**（`04`），而契约与语言无关。
- 负面：无法演示「后端跑起来」；行情源与微信接入的可行性调研如果拖太久，会让 P3 之后的计划失去依据。
- 解除条件：`07-backlog.md` 的 C4（微信接入方式）与 C5（持仓录入方式）有结论，且 P1–P3 完成。
