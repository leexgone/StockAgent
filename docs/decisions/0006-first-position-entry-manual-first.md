# 0006 · 首笔持仓录入：手工逐笔先行，CSV 导入作后续增强

- **状态**：接受
- **日期**：2026-10-28
- **决策者**：leexgone（产品所有者），Claude Code 辅助整理

## 背景

backlog A2：所有界面都假设账户里已有 10 只标的，真实用户第一次打开时没有「录入第一笔」的入口。P4 数据管道的 SQLite schema、导入端点与 P1-T1 空态设计都卡在录入方式（C5）定案上。候选三个：手工逐笔、券商对账单 CSV、截图识别。

## 决定

手工逐笔录入先行：复用 holdings 原型已验证的加减仓抽屉表单（整手 / 涨跌停 / 费用 / 摊薄校验口径已在 `zimu-domain` 与 TS 共享层实现）；券商对账单 CSV 导入列为 P4 后续增强单独立项；截图识别不做。

## 选项与取舍

- **手工逐笔（选）**：交互与校验现成——holdings 抽屉就是录入表单，P4 零新增解析层；个人持仓规模（≤20 只）一次性录入成本可接受。代价只有首次录入略繁琐。
- **券商对账单 CSV（延后为增强）**：批量导入省事，但各家券商导出格式不一，需要解析 + 列映射 + 纠错 UI，P4 工期显著变长；对账单是敏感文件，必须只本地解析、永不入库（git 意义上的库）。与手工先行不冲突——schema 是同一套，增强时只加解析与预览确认层。
- **截图识别（不选）**：依赖 OCR/视觉模型，成本价、数量等字段识别错误会污染全部派生数字，必须再配人工核对界面；复杂度与风险最高，对单人使用的个人工具收益不成比例。

## 后果

- P1-T1 空态壳解锁：「录入第一笔」入口即手工表单抽屉，空态引导按此设计。
- P4-T1 收敛为「手工录入流程实现」，schema 第一版只需服务表单字段（须能存奇零股持仓，见 backlog B12）。
- 后续要做 CSV 增强时单独立项，存储与校验层不变；要做截图识别则须重开新 ADR。
